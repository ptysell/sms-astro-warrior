## <a id="velocity"></a>Enemy movement model (velocities, directions, aim & flight tables)

**Verifier verdict: CONFIRMED.** Independently re-derived from the ROM bytes, the decode is substantively correct and its load-bearing numbers are ROM-EXACT. The magnitude+direction model is real: dispatcher @0x0405 pushes return address 0x0416; the shared integrator @0x0416 reads dir bitfield +0x02 (bit0=up Y-, bit1=down Y+/despawn Y_hi>=0xC8, bit2=left X-/despawn X_hi<0x10, bit3=right X+/despawn X_hi>=0xF8) and applies |vy|=+0x0C/0D, |vx|=+0x0E/0F — verified opcode-for-opcode. Dispatch table @0x0518 (type*2) matches every handler address. The aim primitive @0x18fd + word-pointer table @0x19C0 -> 4-byte records @0x199C-0x19BF is a unit-speed polar table of constant magnitude 0x01E0 = 1.875 px/f for every angle (verified). Bank6 is paged to slot2 (LD A,6;LD(0xFFFF),A @0x00B9) before the updater @0x00C1, so CPU 0xA000 = file 0x1A000; the sharlin flight-script engine (type 0x18 @0x4A5F: +0x13 -> ptr table 0x4B6A -> scripts @0xA0A8; 4-byte steps [dur,dir-idx->0x4B5F,sprite,vel-off->0xA000]) and the 0xA000 velocity table (rings 0.5/1.0/1.5/2.0/3.0 px/f, 4-byte [Xlo,Xhi,Ylo,Yhi]) are byte-exact, including off 0x54=(2.0,0), 0x60=(1.414,1.414), 0x6C=(0,2.0). All 17 per-handler velocity/accel decodes (cult/zanix/shamir/sharlin/delta/arbleby/aster/ashion/burdle/caborn/dririt/tinker/kyra/ufolick/triat/tricker/gyron) match the actual immediates. Both of the analyst's flagged open questions (0x5CAE semantics, hence shamir/tinker final speeds) are now RESOLVED. One factual error found (the +0x01-bit0 gate is a despawn/kill flag, not a movement freeze) but it does not affect normal motion. This table is ready to embed verbatim in GameSim.

### Summary
Enemy motion is NOT stored as a signed velocity per entity. It is a MAGNITUDE + DIRECTION-BITS model integrated by a single shared routine at 0x0416 (runs after every type handler returns; the handler's return address 0x0416 is pushed by the dispatcher at 0x0405). Layout: +0x08/+0x09 = Y (8.8 LE), +0x0A/+0x0B = X (8.8 LE), +0x0C/+0x0D = |Y-step| per frame (8.8), +0x0E/+0x0F = |X-step| per frame (8.8), +0x02 = direction bitfield (bit0=UP Y-=, bit1=DOWN Y+=, bit2=LEFT X-=, bit3=RIGHT X+=). So the SAME positive magnitude in +0x0C/+0x0E is applied with a sign chosen by the +0x02 bits (e.g. 0x02=down, 0x0A=down+right, 0x06=down+left, 0x09=up+right). Handlers set the magnitudes/direction; the integrator does the add each frame. Two shared velocity sources feed the handlers: (1) an AIM-AT-PLAYER primitive 0x18fd that writes both +0x02 and (+0x0C..+0x0F) from a polar table at 0x19C0 whose every entry is a UNIT-SPEED vector of total magnitude 0x01E0 = 1.875 px/f (used by cult, shamir, tinker and every enemy bullet type 0x14 @0x18EE); (2) a FLIGHT-SCRIPT engine (sharlin/type 0x18) whose per-member script index +0x13 selects a script via table 0x4B6A, and each 4-byte script step [duration, dir-index→table 0x4B5F, sprite, vel-index] reads a 4-byte (X,Y) velocity vector from a polar table based at CPU 0xA000. Both 0xA000 and the scripts (0xA0A8..0xA305) live in BANK 6 (file 0x1A000 / 0x1A0A8), which is paged into slot-2 (LD A,6;LD (0xFFFF),A at 0x00B9-0x00BB) right before the entity-update pass at 0x00C1. All values below are 8.8 fixed read directly from ROM; px/f = value/256. The current sim's INFERRED best-fit speeds can be replaced with these exact figures.

### Findings
- **Shared velocity integrator (the core of the whole model)** `0x0416 (dispatcher pushes it at 0x0405; body 0x0416-0x0488)` [ROM-EXACT/high]
  0x0416: after each handler the mover runs. C=(IX+02) direction byte; RRC C 4x. bit0 set -> Y(+08/09) -= (+0C/+0D) [UP]; bit1 -> Y += (+0C/+0D), deactivate if Y_hi>=0xC8(200) [DOWN]; bit2 -> X(+0A/0B) -= (+0E/+0F), deactivate if X_hi<0x10(16) [LEFT]; bit3 -> X += (+0E/+0F), deactivate if X_hi>=0xF8(248) [RIGHT]. Bit0 of +0x01 (checked at 0x0419) freezes movement. So per-frame velocity = (+0x0C/+0x0D as |vy|, +0x0E/+0x0F as |vx|) with signs from +0x02. Off-screen despawn bounds: Y>=200, X<16, X>=248.
- **Aim-at-player primitive 0x18fd + polar unit table 0x19C0 (1.875 px/f)** `0x18fd (routine); 0x19C0 (ptr table); 0x199C-0x19BF (4-byte vel records)` [ROM-EXACT/high]
  0x18fd computes dx=player_Xhi(0xC60B)-(+0x0B), dy=player_Yhi(0xC609)-(+0x09); sets +0x02 direction bits from the signs; picks the larger axis; via divide 0x1988 builds an angle bucket and reads a WORD pointer from table @0x19C0 (16 word entries -> records 0x199C..0x19BF), each record = 4 bytes [dominant_lo,dominant_hi,other_lo,other_hi] copied to +0x0C/+0x0D (vy) and +0x0E/+0x0F (vx) (axes swapped in the X-dominant branch at 0x195C). Decoded records: total speed is CONSTANT 0x01E0 = 1.875 px/f for every angle, split (vy,vx) from (1.875,0) at pure-axis to (1.328,1.328)=0x0154 at 45deg. Used by cult(0x18fd@state0), shamir, tinker, and enemy bullet type 0x14 (handler 0x18EE falls straight into 0x18fd).
- **Flight-script velocity table @ CPU 0xA000 = FILE 0x1A000 (bank 6) — the ~0xA000 table the docs asked about** `0x4B6A (ptr table); file 0x1A000 (vel table, CPU 0xA000); file 0x1A0A8+ (scripts, CPU 0xA0A8+); 0x4B5F (dir-index table)` [ROM-EXACT/high]
  Sharlin (type 0x18 @0x4A5F) is script-driven. +0x13 indexes ptr table 0x4B6A (10 words: 0xA0A8,0xA0C1,0xA0DA,0xA147,0xA1B4,0xA1DD,0xA206,0xA24F,0xA298,0xA305). Each script step (parsed at 0x4AF4-0x4B3B) = 4 bytes: [b0=duration frames (0xFF=end), b1=dir-index into 0x4B5F, b2=sprite +0x23, b3=byte offset into 0xA000]. The vel table @0xA000 is POLAR: 4-byte entries [Xlo,Xhi,Ylo,Yhi], grouped in rings of 7 by magnitude 0.5,1.0,1.5,2.0,3.0 px/f sweeping X->Y (all POSITIVE; sign from +0x02). e.g. off 0x6C=(0,2.0), 0x60=(1.414,1.414), 0x54=(2.0,0). Scripts + table are in bank6 (file 0x1A000/0x1A0A8), paged to slot2 by LD A,6;LD(0xFFFF),A at 0x00B9 immediately before the updater at 0x00C1. Sharlin's own scripts use the 2.0-ring at down-left/down-right dirs => centre-stream curving at 2.0 px/f.
- **Direction-index table 0x4B5F (script dir-index -> +0x02 bits)** `0x4B5F` [ROM-EXACT/high]
  11 bytes @0x4B5F = 00 00 00 00 00 0A 06 00 00 09 05. idx5->0x0A(down-right), idx6->0x06(down-left), idx9->0x09(up-right), idx10->0x05(up-left); all others 0x00 (no move). Sharlin scripts only use idx 5/6 (down diagonals).
- **cult (type 0x15 @0x4842)** `0x4842 init; 0x487B/0x4893/0x48CD states; table 0x48DE` [ROM-EXACT/high]
  Init (0x4848) sets NO velocity/direction (relies on slot=0). state0 (0x487B): DEC +0x13 delay, then CALL 0x18fd => AIM at player = 1.875 px/f total toward player, direction into +0x02. state1 (0x4893): every 16f (+0x21) subtract 0x0020 from |vx| (+0x0E/+0x0F) i.e. -0.125 px/f each 16 frames -> converges toward centre; when it crosses 0, negate and go state2. state2 (0x48CD): add 0x0008 (+0.03 px/f) to |vx| per frame. Net: delayed launch, aimed descent ~1.875 px/f with X drifting toward centre. vx-decay = 0x20 per 16f, vx-rebuild = 0x08/f.
- **zanix / 'X' turret (type 0x16 @0x48E4)** `0x48E4 init; states 0x4925/0x4932/0x4948/0x496A; table 0x49A4` [ROM-EXACT/high]
  Init: +0x02=0x0A (down+right). state1 (0x4932) sets +0x0C=0x80 => vy=0x0080=0.5 px/f down (relies on +0x0D=0), and +0x0E=0x80,+0x0F=1 => vx=0x0180=1.5 px/f. state2 (0x4948): subtract 0x0040 (0.25 px/f) from |vx| per frame until <0, then vx=0, state3. state3 (0x496A): add 0x0040/frame to |vx| until it reaches 0x0180 again, then loop to state1; fires (0x18a6) gated. Motion: constant 0.5 px/f descent + horizontal sweep oscillating |vx| 0..1.5 at accel 0x40/f (0.25 px/f^2).

A single-slot ROM trace of one zanix shows X oscillating ~92↔131 (centred ~111) while descending 0.5 px/f; it stays near centre (peaks ~130, never reaches the X≥248 despawn edge) and exits the BOTTOM at ~y199 after ~400 frames. NOT a monotonic rightward drift. The GameSim `ZanixSweep` pendulum is therefore faithful; a "drift-only, no-flip" model is WRONG (it collapses the idx12–15 population and raises DIVERGENCE). ## <a id="boss"></a>Boss driver & multi-part model

**Verifier verdict: CONFIRMED.** I disassembled every cited address in AstroWarrior.sms and the decode holds up byte-for-byte, including its headline correction. VERIFIED ROM-EXACT: (1) Unified driver at 0x3B94 gated by 0xC24E (set 0x0DD2, tested 0x0CFC -> JP nz 0x3B94; the ONLY reference to 0x3B94 is that JP — no CALL exists, so it is a tail-jumped frame handler), 3-word stage table @0x3BA8 = {Galaxy 0x3BAE, Asteroid 0x3C6C, Nebula 0x3CFF} indexed by 0xC25B. (2) THE CENTRAL CORRECTION IS CORRECT: 0xE020/0xA858/0xD030 are NOT attack-script pointers. (3) 2-phase movement timer 0xC2E0=0x05DC (1500f) with JP z,0x3DD7 to permanent player-homing; Nebula circular table @0x3E6B (6-byte stride, 32 steps, cos 0xC0->0 / sin 0->0xC0, 0x88 at 45deg) confirmed. (4) All 3 boss records byte-exact (Galaxy 5x0x28 @0x44FC, Nebiros 5x0x29 @0x4611, Belzebul 0x2D+4x0x2C+4x0x2B @0x481D); every handler, state table, hit counter, fire routine and layout table confirmed. Segment gates 0xC211 CP 0x40 (Galaxy/Nebiros) / CP 0x3F (Belzebul); satellite-then-core exposure via 0xC282>=4; core 8-hit; defeat 0x5706 sets reward idx4, clears 0xC282, sets defeat flag 0xC2C1, clears 12 bullet slots @0xCD00, chain-despawns pieces via each handler's 0xC2C1 check -> 0x5B9C (SET 0,(IX+1)). Anchor 0x2A @0x105F (flags 0xA2, Y=0x40, X=0x60, 384-frame timer, sprite 0x83+2*stage) confirmed via dispatch @0x056C. ### Summary
Decoded the complete Astro Warrior boss architecture. It is ONE unified system, not two: a shared "boss driver" at 0x3B94 (gated by boss-active flag 0xC24E, dispatched per-stage by 0xC25B) animates the whole formation via RAM globals 0xC2C2/0xC2C3/0xC2C5, and each hittable piece is a normal pool entity (types 0x28/0x29/0x2B/0x2C/0x2D) whose active-state handler copies those globals for position/motion and runs its own hit/fire logic. MAJOR CORRECTION: the "per-phase attack-script pointers 0xA858 (Asteroid) and 0xD030 (Nebula)" — plus Galaxy's equivalent 0xE020 — are NOT code/data pointers and there is no attack bytecode behind them. They are packed player-X TRACKING CLAMP BOUNDS: the 16-bit value is loaded once per stage into 0xC2E2 and read exactly once, at 0x3DF3, where E=low byte=left bound and D=high byte=right bound clamp the boss's horizontal homing target. Galaxy 0xE020→[0x20,0xE0], Asteroid 0xA858→[0x58,0xA8], Nebula 0xD030→[0x30,0xD0]. The real phase machine is a 2-phase MOVEMENT timer (0xC2E0=1500 frames of stage-specific scripted motion, then permanent home-to-player). Firing lives entirely in the per-entity handlers (aimed bullets via velocity table 0x199C). All three bosses use a "destroy the satellites to expose the core, then 8 hits" structure with chain-despawn via defeat flag 0xC2C1.

### Findings
- **Boss driver 0x3B94 is the unified movement engine; gated by 0xC24E, dispatched per-stage by 0xC25B** `0x3B94 / 0x0CFC / 0x3BA8` [ROM-EXACT/high]
  Main loop @0x0CFC: `LD A,(0xC24E); OR A; JP nz,0x3B94` — when boss-active flag 0xC24E!=0, control jumps into the driver every frame. 0xC24E is set to 1 at 0x0DD2 (`LD A,1; LD (0xC24E),A`) in the wave-advance path. Driver head @0x3B94: `LD A,(0xC25B); ADD A,A` indexes 3-word jump table @0x3BA8 = {Galaxy 0x3BAE, Asteroid 0x3C6C, Nebula 0x3CFF}. Each per-stage body clears/writes globals 0xC2C2 (motion-command byte), 0xC2C3 and 0xC2C5 (16-bit position/velocity components). No `CALL 0x3B94` exists anywhere (grep 943b → only the 0x0D00 JP); it is a tail-jumped frame handler.
- **CORRECTION: 0xA858/0xD030/0xE020 are player-X clamp bounds, NOT attack-script pointers — no attack bytecode exists behind them** `0x3DF3 / 0x3BD6 / 0x3C8A / 0x3D16 / 0xC2E2` [ROM-EXACT/high]
  Each per-stage driver init writes ONE constant to 0xC2E2: Galaxy @0x3BD6 `LD HL,0xE020; LD (0xC2E2),HL`; Asteroid @0x3C8A `LD HL,0xA858`; Nebula @0x3D16 `LD HL,0xD030`. 0xC2E2 is READ exactly once ROM-wide, at 0x3DF3 `LD DE,(0xC2E2)` inside the phase-2 homing routine, then: `LD A,(0xC60B){playerX}; CP E; JR nc; LD A,E; CP D; JR c; LD A,D` — i.e. clamp target-X to [E=low byte, D=high byte]. So the bytes are a packed [leftBound,rightBound]: Galaxy 0xE020=[0x20,0xE0]=[32,224]; Asteroid 0xA858=[0x58,0xA8]=[88,168]; Nebula 0xD030=[0x30,0xD0]=[48,208]. grep for 2ae2c2/3ae2c2 (other read forms) returns nothing. The prior doc's 'per-phase attack scripts behind 0xA858/0xD030 — not yet decoded' was a misinterpretation; there is no per-phase attack bytecode.
- **Phase state machine = 2-phase MOVEMENT timer (0xC2E0), shared by all stages** `0x3DD7 / 0xC2E0 / 0xC2C1` [ROM-EXACT/high]

### Summary
Decoded bank-4 sprite pixels for all 18 grunt romTypes and 3 boss segment-types, and — crucially — recovered the romType->sprite mechanism from the ROM, then cross-checked every naming against the documented GameFAQs/community roster BY ROM-EXACT WAVE COUNT. Mechanism (ROM-EXACT): each entity handler writes an appearance/animation index (IX+3); the renderer at 0x04B5 reads frame_ptr = word[0x1187 + (IX+3)*2]; the descriptor is triples [Yoff,Xoff,VRAMtile] terminated by 0x80 (consumer @0x04C9); sprites are 8x16 hardware pairs (reg1=0xA2) composed column-major (TL=n,BL=n+1,TR=n+2,BR=n+3). The graphics loader @0x07E3 pages bank4 and copies a 0xE00-byte (112-tile) PER-VARIANT block -- source 0x8000/0x8E00/0x9C00 = file 0x10000/0x10E00/0x11C00 = file-tiles 0x00/0x70/0xE0 for Galaxy/Asteroid/Nebula -- into the SAME VRAM slot 0x1200 (tile 0x90). So file_tile = (VRAMtile-0x90) + block_base, and the three zones alias the same VRAM/descriptor slots with different pixels. This mapping is self-consistent (Cult ring-disc, X-turret land exactly where predicted) and the decoded per-type wave counts (table @0x3FA3) match the FAQ roster: Galaxy 60/82/28/32/32/18, Asteroid 88/84/8/34/28/48, Nebula named sum = 168 exactly. ### Verifier additions (load-bearing facts the decode missed or under-stated)
- Renderer descriptor is fully specified for the port's sprite ripper: loop @0x04C9-0x04F1 reads 3-byte entries [Yoff,Xoff,tile]; Yoff+=(IX+9)=entity screen-Y into SAT Y-table @0xC219, Xoff+=(IX+11)=entity screen-X into SAT XN-table @0xC21B with the tile byte following; a piece whose Yoff+base==0xD0 is skipped (INC DE x3); the SAT is capped at 64 sprites (L==0x40 guard); list terminates on the first byte==0x80. So a faithful ripper: frame=word[0x1187+(IX+3)*2], walk triples to 0x80, file_tile=(tile-0x90)+block_base.
- 0x16's frame animation is a THREE-frame range, not two: init sets IX+4=0x41 (min) and IX+5=0x43 (max) alongside IX+3=0x41, so the turret cycles X(0x41)->+(0x42)->0x43. This strengthens the 'no separate Curos' finding — frame 0x42 is unreachable as any type's base sprite (confirmed: no handler inits (IX+3)=0x42).
- 0x22 reward index (IX+0x1B)=2 -> 200 pts (ROM-EXACT @0x5150 handler). This CORRECTS the older parity-findings.md 4a which measured '22 -> 100 pts (medium confidence)'; the new decode's 200 is right. Same for the reward table decode: score @0x5C60 words are 0x0000/0x0001/0x0002/0x0010 and the live score has a fixed 00 low byte, so idx1/2/3 = 100/200/1000.
- Record reader @0x3F5B-0x3F92 confirmed: entity gets type at +0x00, then LD BC,0x13 places record byte1->+0x13, byte2->+0x14, byte3->+0x15; the wave member counter is 0xC281 (*4 = record stride), matching the decode's 4-byte [type,b1,b2,b3] layout exactly.
- block_base per zone is tied to BOTH selectors via 0xC240 mod 3: variant0/Galaxy uses graphics 0x8000(file 0x10000, tile-base 0x00) AND wave-root 0x3FA9; variant1/Asteroid 0x8E00(0x10E00, base 0x70) + root 0x4029; variant2/Nebula 0x9C00(0x11C00, base 0xE0) + root 0x40A9. Because all three copy into the SAME VRAM slot 0x90 and share the SAME frame-descriptor table @0x1187, the same (IX+3) index renders different pixels per zone — so the port's Bestiary sprite art MUST be zone-scoped, exactly as the decode states.

## <a id="audio"></a>Audio: SN76489 driver, tracks & SFX

**Verifier verdict: CONFIRMED.** Independent re-disassembly of every cited address confirms the audio decode almost in full. The driver frame entry @0x34CA (CALL 0x352E mailbox, CALL 0x34FF fade, 6x0x20-byte channel loop from 0xDC05), the per-channel interpreter @0x362B, the note/command/duration decoder @0x3791 (>=0xE0 command / 0x80-0xDF note / 0x00-0x7F duration; transpose IX+5; portamento target; optional-vs-mandatory duration peek @0x381E/0x37DE; length = durByte*tempo via multiply @0x39F0), the command mailbox @0x352E with data table @0x3556 (all 19 pointers byte-exact) and handler table @0x357E (derived as 0x3556+idx*2+0x28), the 73-word pitch table @0x395E (REST + 72 notes, halving every 12, table ends 0x39EE / code begins 0x39F0), the opcode jump table @0x383C (all 16 E0-EF targets) and every opcode's implementation, the PSG byte-writer @0x392D (BIT 2,(IX) mute-check then OUT (0x7F)), the reset/mute @0x3935 (LDIR clear of 0xDC01+ then OTIR of 9F BF DF FF), the 9-byte-header LDIR copy @0x3602, the envelope @0x3429 (8 progs) and vibrato @0x3475 (4 progs) pointer tables and their nibble-program bytes, the fade @0x34E7/0x34FF (13 steps x 20 frames ~260f), the boot mute @0x0042, all trigger sites (fire=0x87 @0x0AFE, small-expl=0x8C @0x5C14 sprite0x14, big-expl=0x90 @0x5C25 sprite0x17), the stage-BGM table @0x00E2 = {0x82,0x83,0x92}, the SFX priority/channel-borrow model (fire=0, boss/jingle=4, noise=8, powerup=0x20), and the 11-site OUT(0x7F) census all hold exactly as claimed. Exactly one byte-level error found (tone latch table). Confidence: high for all ROM-EXACT items (disassembled directly). The role/absence claims (which track is which zone; 6 unused leftover tracks; no separate boss/ending music) are consistent with the confirmed stage table and trigger sites but are inherently MEASURED/inferred, not byte-provable.

### Summary
Astro Warrior's audio is a full data-driven SN76489 sound engine living in bank 0 (file==CPU address). All PSG output goes through OUT (0x7F); the 11 write sites are: boot-mute 0x0042-0x0050, the driver's per-frame tone/vol writer 0x3932, and hard-coded channel mutes at 0x34F7/0x3950/0x3955/0x38D0 plus SFX-borrow mutes 0x35D8/0x35E8. The DRIVER frame entry is 0x34CA (called once/frame from the VBlank handler at 0x0381): it (1) processes a one-byte command mailbox at 0xDC00 (dispatch 0x352E), (2) ticks a fade counter (0x34FF), (3) updates 6 channel-state blocks via the per-channel bytecode interpreter at 0x362B. Game code requests a sound by writing a command byte 0x81..0x93 to 0xDC00; command idx = byte-0x81 selects a data pointer from the table @0x3556 (20 words) and a start-handler from the parallel table @0x357E. Each track's data = [nChannels] then N x 9-byte channel headers (flags, PSG-channel, tempo, stream-ptr, transpose, vibrato-prog, envelope-prog, volume); each channel's stream is a note/duration/command bytecode. Notes index a 6-octave chromatic period table @0x395E (byte 0x81=A2 ... 0xC8=G#8, period halves every 12 semitones). I mapped all 19 commands to semantics: 3 zone BGMs (Galaxy/Asteroid/Nebula), a title theme, an attract theme, 2 event jingles, and 6 SFX; 6 further commands are composed-but-unused leftovers. There is no separate boss/ending/game-over music (the game loops forever; stage-transition/game-over just fades via CALL 0x34E7).

### Findings
- **Music driver frame entry @0x34CA** `0x34CA` [ROM-EXACT/high]
  0x34CA: CALL 0x352E (process command mailbox 0xDC00); 0x34CD: CALL 0x34FF (tick fade); 0x34D0: LD IX,0xDC05; LD B,6; loop{ BIT 7,(IX); CALL nz,0x362B; DE=0x20; ADD IX,DE } DJNZ. Called once per frame from 0x0381 (inside VBlank ISR at 0x030F). This is THE sound update tick.
- **Per-channel bytecode interpreter @0x362B** `0x362B` [ROM-EXACT/high]
  Core sequencer. 0x362B increments the 16-bit elapsed counter (IX+0x0C/0x0D), compares to note-duration (IX+0x0A/0x0B); when equal CALLs the event-fetch 0x3791. Then applies vibrato (via IX+6/table 0x3475), envelope (via IX+7/table 0x3429), writes the effective 10-bit period to the PSG tone register (0x36DE-0x3702) and the attenuation to the PSG volume register (0x3703-0x3713). The actual PSG byte-writer is 0x392D: BIT 2,(IX) RET nz (skip if channel muted); else OUT (0x7F),A.
- **Event-fetch / note decoder @0x3791** `0x3791` [ROM-EXACT/high]
  Reads next stream byte at ptr (IX+0x03/0x04). byte>=0xE0 => command (jump table @0x383C, index=byte&0x1F). byte 0x80..0xDF => NOTE: semitone=byte-0x80 (0x80=REST), +IX+5 transpose, *2 index into period table 0x395E -> IX+0x10/0x11. byte 0x00..0x7F => bare DURATION. Duration is a following byte<0x80: OPTIONAL for plain tone notes (peek @0x381E, reuse previous if next byte>=0x80), MANDATORY when portamento(bit5) or absolute(bit3) mode is set (0x37DE). Duration_frames = durByte * tempo(IX+2), via the 8x8->16 multiply at 0x39F0.
- **Command mailbox + dispatch @0x352E; data table @0x3556, handler table @0x357E** `0x3556` [ROM-EXACT/high]
  0x352E: A=(0xDC00); if BIT7 clear OR >=0x94 => JP 0x3935 (silence+reset RAM); SUB 0x81 (m=>RET, 0x80=idle); idx=A-0x81; data ptr = word[0x3556+idx*2]; handler = word[0x357E+idx*2]; E=(0xDC01) priority; JP handler. Data ptrs (cmd:ptr): 81:2A7D 82:2BD5 83:2E7F 84:3057 85:3149 86:31AA 87:321F 88:3247 89:3266 8A:329F 8B:3339 8C:334D 8D:3369 8E:33DB 8F:33EA 90:340D 91:2A4D 92:2992 93:297E.
- **Track/SFX -> address map with roles (all 13 used commands)** `0x00E2` [MEASURED/high]
  BGM (start-handler 0x35B3/0x35A9, resets all, plays from 0xDC05): 0x81 data 0x2A7D = TITLE theme (played 0x1DE7, waits for Start then JP 0x00A0); 0x82 data 0x2BD5 = GALAXY stage BGM (loop point 0x2C0E); 0x83 data 0x2E7F = ASTEROID BGM; 0x92 data 0x2992 = NEBULA BGM (0x82/83/92 chosen by stage-counter 0xC25B via table @0x00E2 bytes 82 83 92); 0x86 data 0x31AA = ATTRACT/demo BGM (0x028E/02B9/02E4). Jingles: 0x91 data 0x2A4D = rising 4-voice chord sweep, timed cue @0xC291 (screen-transition/warp); 0x8A data 0x329F = event jingle, flag 0xC298 (extra-life/upgrade). SFX (overlay, borrow a PSG channel by SET 2 on the music block): 0x87 data 0x321F = PLAYER FIRE (played on bullet launch @0x0AFE, bullet handler type2@0x0AB2); 0x88 data 0x3247 = fire/power-shot variant (0x0B7E); 0x89 data 0x3266 = POWER-UP pickup (spawns wing-pods @0x0925); 0x8C data 0x334D = enemy EXPLOSION (death routine 0x5C0C, sprite 0x14; also 0x281C); 0x90 data 0x340D = big EXPLOSION (death 0x5C1B, sprite 0x17); 0x8E data 0x33DB = BOSS-HIT/segment explosion (0x56F6/57E1/57F5/5B86 boss death, and 0x0B1E).
- **Six commands are composed-but-UNUSED leftovers** `0x3057` [ROM-EXACT/high]
  No 0xDC00 write anywhere targets cmd 0x84 (data 0x3057, 4ch), 0x85 (0x3149, 3ch), 0x8B (0x3339, 1ch noise), 0x8D (0x3369, 3ch), 0x8F (0x33EA, 2ch), 0x93 (0x297E, 1ch). All 21 stores to 0xDC00 were enumerated; the only computed store is the stage table @0x00E2 (yields 82/83/92). The 3 unused FULL tracks (0x84/0x85/0x8D) were likely intended as boss/ending/game-over music that was cut - the shipped game loops zones forever (no ending) and game-over just fades.
- **Track data format: header block** `0x3602` [ROM-EXACT/high]
  data[0] = nChannels (1..4). Then nChannels x 9-byte channel header, copied verbatim into a channel state block by 0x3602 (LDIR 9). Header bytes: +0 flags (bit7=active, bit5=portamento-on, bit3=absolute-period-mode, bit2=muted); +1 PSG channel (0..3: 0/1/2=tone, 3=noise; low nibble selects latch); +2 tempo (frames-per-duration-unit multiplier); +3/+4 stream pointer (LE); +5 key transpose (added to every semitone); +6 vibrato program (0=off, else idx into 0x3475); +7 envelope program (0=off, else idx into 0x3429); +8 base volume level 0..15 (0=silent-ish,15=loud). Verified against all 19 tracks (e.g. 0x2A7D=4ch tempo5; 0x2A4D=4ch same-stream transpose 0/3/7 chord).
- **Note pitch table @0x395E (6-octave chromatic, tuned to A)** `0x395E` [ROM-EXACT/high]
  73 x 16-bit SN76489 tone periods, index = (byte-0x80)+transpose. idx0=0x0000=REST. idx1=0x03FF..idx72=0x0011, strictly halving every 12 entries (12-TET). Frequency = 3579545/(32*period). byte 0x81=A2(109Hz), 0x8D=A3, 0x99=A4(437Hz~440), 0xA5=A5, 0xB1=A6, 0xC8=G#8(6580Hz). Valid note bytes 0x81..0xC8; bytes >=0xC9 read past the table into code (invalid).
- **Sequencer command opcodes 0xE0-0xEF (jump table @0x383C, index byte&0x1F)** `0x383C` [ROM-EXACT/high]
  E0(->3864) SET_TEMPO IX+2 (1 param); E1(->3875) SET_VOL IX+8 (1); E2(->38B9) STOP/END-SFX: RES 2 on music blocks 0xDC25/45/65 (un-borrow), 0xDC01=0, (IX+0)=0 note-off, OUT 0xE4, then POP HL x2 (unwinds fetch+loop) - this is how every SFX terminates; E3(->387A) NOISE_CTRL: writes 0xE0|param to PSG noise reg, sets bit6 if param&3==3 (1); E4(->3891) SET_ENV IX+7 (1); E5(->389B) GOTO absolute addr = loop point (2); E6/E7(->38A1/38A7) PORTA on/off (bit5); E8/E9(->38AD/38B3) ABS-period mode on/off (bit3); EA(->38D8) CALL subroutine using per-channel stack ptr IX+9 (2); EB(->38F3) RETURN from subroutine; EC(->3906) LOOP: named counter at IX+(param1+0x17), count param2, 2-byte back-target (5 bytes total); ED(->3896) SET_VIB IX+6 (1); EE(->385C) TRANSPOSE += param, IX+5 (1); EF(->3869) VOL relative adjust (1). Bytes 0xF0-0xFF index past the valid table (unused).
- **PSG hardware write construction (tone + volume latch tables)** `0x371A` [ROM-EXACT/high]
  Volume byte: table @0x371A = {90,B0,D0,F0} (channel volume-latch, indexed by PSG channel) OR'd with attenuation IX+0x16 (0=loud..15=silent); written via 0x392D. Tone byte pair: latch table @0x3716 = {80,A0,C0,E0}; first write = 0x80|(chan<<5) | (period & 0x0F); second write = (period>>4) & 0x3F. So standard SN76489: 1cc0dddd then 00dddddd. Rest (period 0) forces attenuation 15. Channel muted if BIT 2 of block+0 set (SFX borrow), suppressing the OUT.
- **Volume-envelope programs @0x3429 (8 progs) and processor @0x3721** `0x3429` [ROM-EXACT/high]
  Pointer table @0x3429 (8 words, idx=prog#-1) -> nibble-packed volume programs (2 steps/byte). Each frame one nibble is consumed (phase IX+0x0E): value 3..F = volume offset applied as (0xF0|n)+IX+8+1 then CPL&0x0F -> attenuation (F=loudest, decreasing = decay); nibble 0x1 = sustain/hold (re-reads same step); 0x2 = release/note-off (attenuation 0x0F). Prog1@0x343D = FF 02... (fast pluck+decay); prog5-8 = longer decays. Used by every melodic channel (header +7).
- **Vibrato programs @0x3475 (4 progs) and processor @0x375B** `0x3475` [ROM-EXACT/high]
  Pointer table @0x3475 (4 words) -> nibble-packed period-delta programs (phase IX+0x0F). Each frame a signed nibble delta is added to the base period -> pitch wobble (0x3789 ADD HL,DE -> IX+0x12/0x13). prog1@0x3489 = EE EE EE EE EE FF... (shallow, ~-2 wobble); prog3@0x34A2 = FE DB AB CD EF... (deep vibrato). Selected by header +6 / ED command. Same 0x1=hold, 0x2=end convention as envelopes.
- **Sound-engine RAM map (work area 0xDC00-0xDCC5)** `0xDC00` [ROM-EXACT/high]
  0xDC00 = command mailbox (game writes 0x81..0x93; 0x80 idle; 0x84 internal-busy; >=0x94 stop). 0xDC01 = current SFX priority (new SFX plays only if its priority >= current: fire=0, EE-jingle=4, noise-SFX=8, 0x89=0x20, 0x8F=0x30, BGM=0x80; higher wins). 0xDC02/0xDC03 = fade step-count/sub-timer. Six 0x20-byte channel-state blocks: 0xDC05 music TONE0, 0xDC25 music TONE1, 0xDC45 music TONE2, 0xDC65 music NOISE, 0xDC85 SFX slot A, 0xDCA5 SFX slot B. Block offsets: +0 flags, +1 PSGchan, +2 tempo, +3/4 streamptr, +5 transpose, +6 vib, +7 env, +8 vol, +9 substack ptr, +0A/0B note-duration, +0C/0D elapsed, +0E vib-phase, +0F env-phase, +10/11 base period, +12/13 effective period, +14/15 porta target, +16 attenuation.
- **Silence / reset / fade-out mechanisms** `0x34E7` [ROM-EXACT/high]
  Immediate silence+reset: 0x3935 zeroes 0xDC01..0xDCBC (LDIR) and OTIRs the mute sequence 9F BF DF FF (@0x395A) to the PSG; reached by writing 0xDC00>=0x94, or CALL 0x3935 directly (0x00EC,0x013F,0x1D4A boot/reset). Boot mute routine 0x0042 writes 9F/BF/DF/FF. Multi-step FADE-OUT: CALL 0x34E7 (only caller 0x1040, a stage-transition/game-over path) sets 0xDC02=13,0xDC03=8; 0x34FF decrements every 20 frames, ramping attenuation into channel blocks 0xDC0D/2D/4D, then mutes and sets 0xDC00=0x84 (~260 frames ~4.3s).
- **Player-fire SFX trigger is the bullet spawn** `0x0AB2` [ROM-EXACT/high]
  Dispatch type 2 (player bullet) -> handler 0x0AB2. At init 0x0AEE it sets bullet (IX+1)=0x80,(IX+2)=1,(IX+0x0D)=12 (=12px/frame up, matches shipBulletSpeed) then 0x0AFE: LD A,0x87; LD (0xDC00),A. So cmd 0x87 (data 0x321F) = the shot sound, emitted once per bullet launched.
- **Explosion SFX are keyed to the entity death routine** `0x5C0C` [ROM-EXACT/high]
  Generic enemy death: 0x5C0C sets death-sprite (IX+3)=0x14 and plays 0x8C (data 0x334D, white-noise burst E3 07 then a short pitch-swept noise). 0x5C1B sets (IX+3)=0x17 and plays 0x90 (data 0x340D, longer noise). Boss part/core death (0x56F6,0x57E1,0x57F5,0x5B86) does RES 6,(IX+1) then plays 0x8E (data 0x33DB, a 3-note tonal chord burst on TONE2, envelope 1). So 3 distinct destruction sounds: small (0x8C), large (0x90), boss (0x8E).
- **Galaxy BGM (0x82) verified as looping music with subroutine reuse** `0x2BFA` [ROM-EXACT/high]
  data 0x2BD5 = 4 channels, tempo 4. ch0 stream @0x2BFA is a melodic lead (C#6/D6/E6/B5/A5 phrases) that EA-CALLs a shared phrase @0x2C56 and ends with E5 GOTO 0x2C0E (the loop point). ch1/2 harmony+bass, ch3 noise percussion. This is the primary Galaxy-zone gameplay theme (selected via stage table @0x00E2[0]).
- **Title theme 0x81 flow** `0x1DE7` [INFERRED/high]
  Routine at ~0x1DC8 loads title graphics (VRAM 0x9E00/0x8A00/0xA800/0x5E00), sets timer 0xC020=0x438, plays cmd 0x81 (data 0x2A7D, 4-voice song with EA/EB subroutine + E4 envelope changes), then polls Start/buttons (0x1DFE reads port bits 0x30) and on press falls to 0x1E5D: JP 0x00A0 which begins gameplay (playing the zone BGM). Thus 0x81 is the title/press-start theme, distinct from the three zone themes.
- **Duration/tempo arithmetic (8x8 multiply @0x39F0)** `0x39F0` [ROM-EXACT/high]
  0x39F0: D=0; L=0; B=8; {ADD HL,HL; if carry ADD HL,DE} x8 -> HL = H_in * E. Used at 0x37E5 for note length = durationByte * header-tempo(IX+2), and at 0x3695 for portamento per-frame step = (targetPeriod-basePeriod)/duration. So at tempo=4 a durByte of 15 = 60 frames = 1.0s at 60Hz.
- **SFX priority + channel-borrow model** `0x35F2` [ROM-EXACT/high]
  SFX start-handlers (0x35C0/35F2/35DC/35EE/35BC/35F7) compare their fixed priority against 0xDC01: CP E; JR c,0x3625 (reject, restoring idle 0x80) if new<current. Accepted SFX SETs bit2 on the target music block(s) (e.g. fire SETs 2 @0xDC45 to mute music TONE2), loads its own stream into SFX block 0xDC85 or 0xDCA5, and immediately hard-mutes the PSG channel (OUT DF/FF). On the SFX's E2 opcode the music channel's bit2 is RES (restored). Priorities: fire/0x87,0x88=0, EE/0x8E,0x93=4, noise 0x8C,0x90,0x8B=8, 0x89=0x20, 0x8F=0x30, all BGM=0x80.
- **Absolute-period and portamento note modes (for SFX pitch sweeps)** `0x3804` [ROM-EXACT/high]
  When header flag bit3 (0x08) set (E8), a note is TWO raw bytes [periodHi][periodLo] used directly as the 10-bit tone value (not a table index); bit5 (0x20, E6) adds a slide: reads a second value (start,target) into IX+0x14/0x15 and the interpreter ramps period toward target over the note (0x3695). Fire 0x87 (flags 0xA8) is e.g. 0x0180->0x0020 dur1, rest, 0x00F0->0x0180 dur3 (a laser chirp); explosion 0x8C opens with E3 07 (white noise) then noise-'period' sweeps. Music channels use flags 0x80 (table notes) or 0xA0 (table notes + portamento, e.g. the 0x91 chord sweep).

### Swift port impact
Enables a faithful, data-driven Swift PSG music/SFX subsystem for GameSim instead of ad-hoc tones. Concretely: (1) Port an SN76489 synth at the standard SMS clock 3579545 Hz, 4 channels (3 tone + 1 noise), volume = 15-step attenuation, period = 3579545/(32*p); render at 44.1/48kHz. (2) Port the sequencer: a per-channel state struct mirroring the 0xDC00-block fields (stream ptr, tempo, transpose, note-dur, elapsed, base/effective period, envelope+vibrato phases, sub-stack) driven at 60 ticks/s, decoding the exact bytecode (note 0x80..0xDF over table 0x395E, optional/mandatory duration rules, commands 0xE0-0xEF incl. GOTO/CALL/LOOP, envelope programs @0x3429, vibrato @0x3475). ### Verifier additions (load-bearing facts the decode missed or under-stated)
- Tone-write is GATED at 0x36D8: BIT 6,(IX); JR nz,0x3703 -> if the periodic-noise flag (set by E3 when param&3==3) is set, the 2-byte tone-register write is SKIPPED and only the volume write runs. A faithful port must replicate this gate or periodic-noise channels will emit spurious tone-register writes.
- REST mechanism confirmed at 0x364A-0x3652: when base period (IX+0x10/0x11) == 0, attenuation IX+0x16 is forced to 15 and execution jumps straight to the volume write (0x3703), skipping the tone write. This is exactly how note byte 0x80 (semitone 0 = pitch-table idx0 = 0x0000) silences a channel.
- E2 (end-SFX) @0x38B9 does three things a port must all reproduce: RES 2 on the three music blocks 0xDC25/0xDC45/0xDC65 (un-borrow), reset priority 0xDC01=0 and note-off (IX+0)=0, OUT (0x7F),0xE4 (noise volume-latch/mute) @0x38D0, then POP HL x2 to unwind BOTH the event-fetch return and the interpreter's per-channel call frame so the rest of this tick is aborted.
- Fade-out granularity (0x34FF): the step fires only every 0x14=20 frames (reload of sub-timer 0xDC03) and runs 13 steps (0xDC02 init 13 @0x34E9), writing the descending step value into the base-VOLUME field (offset +0x08) of each music block at 0xDC0D/0xDC2D/0xDC4D; on reaching 0 it CALLs the mute (0x3944) and sets the mailbox 0xDC00=0x84 (internal-busy). ~260 frames ~4.3s.
- Handler-table address is computed, not a separate lookup: @0x3549 the code adds 0x27 to HL after reading the 2-byte data pointer (HL already at data+idx*2+1), giving handler = word[0x3556 + idx*2 + 0x28] = word[0x357E + idx*2]. Both tables share the same index and the dispatch passes the data pointer in BC and the priority (0xDC01) in E into the handler via JP (HL).

### Open questions
- Exact runtime semantics of jingle 0x8A (data 0x329F, flag 0xC298 set at 0x0C83) and sweep 0x91 (data 0x2A4D, timer 0xC291 init=200 at 0x0E95): most likely extra-life/weapon-upgrade and area-transition/warp respectively, but the triggering game state (which entity/screen) was not fully traced - confirm by driving the ROM and watching 0xC298/0xC291 vs on-screen events.
- The 3 unused full tracks (0x84 @0x3057 4ch, 0x85 @0x3149 3ch, 0x8D @0x3369 3ch) are never triggered - they may be cut boss/ending/game-over music; decode them fully if a 'lost tracks' bonus is wanted, but they are not part of shipped playback.
- The precise 0x1=hold / 0x2=end nibble handling and the 0x0-nibble resync branch (0x371E/0x3735) in the envelope/vibrato walkers should be unit-tested against a cycle-accurate trace to guarantee sample-exact envelopes; my read of the branch logic is correct in structure but the rare 0-nibble edge path was not exhaustively simulated.
- SFX streams past their first E2 contain additional bytes (e.g. 0x87 continues after 0x3246) that the driver never reaches because E2 unwinds the stack; confirm no alternate entry replays those tails (they appear to be dead data or a second unused variation).

## <a id="flow"></a>Game flow, screens & the loop

**Verifier verdict: CONFIRMED.** I independently disassembled every cited address and read every cited table from the ROM bytes; the decode is exceptionally accurate. All ROM-EXACT claims held verbatim, including the two headline corrections (sub_2309 @0x2309 is a 6-phase background palette pulse on 0xC238, NOT zone progression; and there is NO ending — 0xC227 is never compared to any limit and the boss driver @0x3B94 dispatches purely mod-3 via table 0x3BA8→{0x3BAE,0x3C6C,0x3CFF}, so the game loops forever). Verified byte-for-byte: boot Reset→0x007C→JP 0x1D40 with no splash; state flag 0xC100 (1/2/4, SET 7 in-game @0x00AC); title build @0x1D40 (strings @0x2052/0x2064, timer 0xC020=0x438=1080 @0x1DE1, sound 0x81); wait-loop @0x1DFB (fire mask 0x30, timeout→demo 0xC100=4, 0xC020=0x708=1800, 0xC264=LD A,R AND 1); demo tape playback @0x06FF-0x071C (bank3, one joypad byte/frame from ptr 0xC260) with init @0x0821 selecting file 0xEA00/0xF100 — and I confirmed those bytes are sparse joypad recordings, not graphics; ISR @0x030F (RESET port 0xDD bit4→title, pause/frame gates, subsystem chain, demo timeout); NMI pause @0x0066/0x0053; superloop @0x00A0-0x00D1 with sole death exit on 0xC225; death/BCD-lives-- @0x0154 and checkpoint respawn @0x0222; GAME OVER @0x02DC (type 0x0D, sound 0x86, 360 frames) + handler 0x0FC0; zone-clear @0x0E92 (200-frame 0xC291, banner type 0x0B @0x0FF9, 14-step scroll wipe, fanfare 0x91); progression @0x0D03-0x0D43 (variant BCD++ @0x0D27, 0xC227++, stage=0xC227 mod3); and the crux LOOP RAMP — variant=0xC240 mod3 @0x3F62 (table 0x3FA3→0x3FA9/0x4029/0x40A9) and enemy-fire gate CP 3 @0x5C06 with suppress-on-carry caller @0x5BF2. I mapped all writes to 0xC240 (only 0x0249 respawn-restore, 0x0D27 zone-advance, 0x1E32 demo) confirming it is never reset mid-game, so fire is silent all of loop 1 (0xC240=0,1,2) and arms at >=3 (loop 2). High-score single value @0x2126, extra-life max-4 @0x20FF (thresholds table 0x211E=0500/1000/1500/2000). Whole-ROM ASCII scan finds no GAME OVER/CONGRATULATIONS/CREDITS/THE END/NAME/ENTER/RANKING strings, confirming no initials-entry and no credits. The decode is a faithful, portable basis for GameSim.

### Summary
Fully decoded Astro Warrior's flow layer from ROM bytes. The whole game runs as ONE top-level state machine keyed on RAM byte 0xC100 (0=idle, 1=P1, 2=P2, 4=demo; bit7=in-game, set at 0x00AC; bit1=2-player; bit2=demo). Boot: Reset 0x0000 -> 0x007C -> JP 0x1D40; there is no separate SEGA-logo splash in bank0 -- 0x1D40 builds the TITLE screen (name-table text via string-writer 0x0575 + table 0x2052: "HIGH SCORE"/"0 PTS."/"PUSH START BUTTON"/"(c)SEGA 1986") and runs a wait-loop (0x1DFB-0x1E15) on the 1080-frame timer 0xC020. Pressing a fire button (0xC012/0xC01A & 0x30) starts a game (0xC100=1/2); timeout drops into an ATTRACT DEMO (0xC100=4) that enters the normal gameplay engine at 0x00A0 but feeds a canned byte-per-frame joypad TAPE from bank 3 (paged 0xFFFF=3) at CPU 0xAA00/0xB100 (file 0xEA00/0xF100) via pointer 0xC260 / enable 0xC262 (0x0712-0x071C); one of the two tapes is chosen by random flag 0xC264. Gameplay is a single superloop 0x00A0..0x00D1 spanning ALL zones/loops, exiting only on player death (0xC225=1 -> JP 0x0130). Death BCD-decrements lives 0xC23F and either respawns from a saved wave-index checkpoint (0x0222) or shows GAME OVER (0x02DC: text entity type 0x0D, music 0x86, 360-frame hold, JP 0x1D40). Zone transitions happen IN-loop: boss-defeat sets 0xC290, the scroll routine 0x0D03 waits 0xC291 frames, plays fanfare (0x91), then advances variant/stage/loop (0x0D21-0x0D37). Two big corrections to prior docs: (1) sub_2309/0xC238 is a background palette-cycle ANIMATION, not zone progression; (2) there is NO ending/credits screen -- the loop counter 0xC227 is never bounded and the boss driver dispatches purely mod-3, so the game loops forever. Also confirmed: single high score (0xC030-C032), NO name/initials-entry screen exists anywhere.

### Findings
- **Boot -> title entry; no separate SEGA-logo splash** `0x0000 / 0x007C / 0x1D40` [ROM-EXACT/high]
  Reset 0x0000: DI/IM1/LD SP,0xDFFE/JR 0x007C. 0x007C clears RAM 0xC000-0xDFFF (LDIR), inits VDP, reads region into 0xC000 (IN 0xDE), CALL 0x060A (delay), CALL 0x0637 (loads 11 VDP regs from table 0x062C), then JP 0x1D40 unconditionally. No logo-screen routine runs in bank0 before the title; the 'SEGA' seen at boot is the small (c)SEGA 1986 name-table text on the title itself (bank-5 0x14000 logo tiles are not used on this path).
- **Top-level state machine flag = 0xC100** `0xC100 (writes 0x1E1B/0x1E3F/0x00AC)` [ROM-EXACT/high]
  0xC100 encodes the whole flow: 1=P1 game, 2=P2 game, 4=demo/attract; SET 7 at 0x00AC marks 'in-game' (so demo=0x84); BIT1=two-player; BIT2=demo. Written in the title wait-loop at 0x1E1B(=4 timeout/demo),0x1E3F(=1/2 start). Read by the input router (0x0672/0x06FF bit2=demo, RLCA bit7=in-game), NMI pause gate (0x0067), ISR demo-timeout (0x0361 bit2), and sub_2309 gate (0x2309: RET if 0). 0xC102 holds 2-player alternation bits (bit1=active player, bit2/bit3=P1/P2 game-over).
- **Title screen build (tilemap text + palette + timer)** `0x1D40 (strings @0x2052/0x2064)` [ROM-EXACT/high]
  0x1D40 pages bank3, DMAs tile/graphics blocks (0x1D6A-0x1D9F) and a 32-byte CRAM palette (0x1D85 CALL 0x0020, src 0xC000... i.e. table region), then writes name-table strings via the string-writer 0x0575 (fmt: count, then {destVRAM, srcPtr}; src = [attr byte][ASCII..0], written char-0x20 + attribute) using layout table @0x2052 (0x1DD5) and HUD/sprite-position table @0x2097 (0x1DDB). ROM ASCII: 0x2064 'HIGH SCORE', 0x2070 '0 PTS.', 0x2078 'PUSH START BUTTON', 0x208B '@ [\]^ 1986' (tile 0x40=(c), 0x5B-0x5E='SEGA', ' 1986'). Sets title/attract timer 0xC020=0x0438(1080) at 0x1DE1, sound cue 0xDC00=0x81 (0x1DE9).
- **Title wait-loop + start detection / timeout** `0x1DFB-0x1E5D` [ROM-EXACT/high]
  0x1DFB-0x1E15: each frame RST8 (frame wait), CALL 0x03D4 (frame subsystems). 0x1DFE LD A,(0xC012);AND 0x30;JR nz,0x1E3F (A=1) = P1 fire/start; 0x1E07 LD A,(0xC01A);AND 0x30 (A=2) = P2 start. 0x1E10 LD HL,(0xC020);OR -> JR nz,0x1DFA loops while timer>0. Start pressed -> 0x1E3F LD (0xC100),A (1 or 2). Timeout (0xC020==0) -> 0x1E1B LD A,4;LD (0xC100),A (demo), re-init 0xC020=0x0708(1800) at 0x1E20, pick random demo/form flag 0xC264 = (LD A,R AND 1) at 0x1E26. Both paths clear wave region 0xCA00 and JP 0x00A0.
- **Attract/demo INPUT STREAM source (the tapes)** `0x06FF-0x071C / init 0x0821 / tapes @0xEA00,0xF100` [ROM-EXACT/high]
  Demo runs the real engine at 0x00A0 with 0xC100=4. Input router 0x066B->0x06FE: after building the live joypad byte, 0x06FF LD HL,(0xC100);BIT2,L; if demo it (0x0706) AND 0x30 -> JP nz,0x1D40 (real fire aborts demo to title); else 0x070B checks 0xC262 bit0, 0x0712 LD A,3;LD(0xFFFF),A (page bank3), 0x0717 LD HL,(0xC260);LD A,(HL);INC HL;LD (0xC260),HL -> ONE tape byte/frame becomes the player input. Tape pointer 0xC260 + enable 0xC262 initialized in the player handler at 0x0821: LD A,(0xC264); HL=0xAA00 if 0 else 0xB100; LD (0xC260),HL; LD (0xC262),1. Tapes live in bank3: CPU 0xAA00->file 0xEA00, CPU 0xB100->file 0xF100. Dumped bytes are sparse joypad values (runs of 0x08/0x04/0x01 dirs, 0x20/0x28 buttons) = byte-per-frame recordings, not graphics.
- **VBlank ISR = frame heartbeat, input history, RESET-to-title** `0x030F-0x0384` [ROM-EXACT/high]
  0x030F: IN A,(0xDD);CPL; shift into input history 0xC01C/0xC01D; XOR/AND to get newly-pressed; AND 0x10 (RESET button, port DD bit4); JP nz,0x1D40 (0x032B) = soft-reset to title any time. 0xC111!=0 -> skip subsystems (pause). 0xC110 = frame-run gate (RST8 @0x0008 sets it to 1 and spins until ISR clears it at 0x0370). Subsystem chain when armed: 0x3A10,0x0394(SAT DMA),0x03AC(scroll regs + palette OTIR),0x2309,0x250C,0x25E4,0x066B(input),0x1F18. 0x035A decrements 0xC020; if 0 and 0xC100 bit2 (demo) -> JP 0x1D40 (demo timeout). 0x037A: if 0xC298 set, sound 0xDC00=0x8A.
- **PAUSE handling (NMI + flag 0xC111)** `0x0066 / 0x0053 / 0x00B2` [ROM-EXACT/high]
  NMI vector 0x0066 (SMS PAUSE button): LD A,(0xC100);BIT7 (in-game?) and BIT2 (demo?) -> only if in-game AND not demo, 0x0072 toggles 0xC111 (CPL). Main loop at 0x00B2: LD A,(0xC111);OR A;JP nz,0x0053; 0x0053 spins (loops while 0xC111!=0) then JP 0x00B1 to resume. ISR also gates subsystems on 0xC111 (0x032E). PAUSE is inert on title/demo.
- **Gameplay superloop + single death exit** `0x00A0-0x00D1` [ROM-EXACT/high]
  0x00A0 entry: CALL 0x00E5 (new-life init: lives 0xC23F=3 at 0x0107, player entity 0xC600=1), 0x0E37, 0x07E3 (per-zone tile load, uses 0xC240 mod3), 0x00D3 (zone BGM), 0x00AC SET 7,(0xC100). Loop 0x00B1-0x00D1: RST8; pause check; page bank6; CALL 0x0CFC,0x03D4(frame update),0x3F2B(wave spawner),0x19E0; 0x00CA LD A,(0xC225);OR A;JP nz,0x0130. So the SAME loop covers every zone and every loop iteration; it breaks out only when 0xC225!=0 (player destroyed, set at 0x0C94 SET 0,(IX+1);LD (0xC225),1).
- **Death / lives / checkpoint respawn** `0x0130 / 0x0222` [ROM-EXACT/high]
  0x0130: per-player (0xC100 bit1) path. Save live score 0xC232-C234 -> 0xC130 (P1)/0xC133 (P2). BCD decrement lives: LD A,(0xC23F);ADD A,0x99;DAA;LD (0xC23F),A (0x0154). If result 0 (Z) -> game over (0x02DC / per-player 0x0286/0x02B1). Else save checkpoint: 0xC211..0xC218 (8 bytes)->0xC140/0xC150, plus 0xC240/0xC25B/0xC227. Respawn 0x0222: clear 0xC200-0xDEFF, player 0xC600=1, RESTORE checkpoint (0xC211 wave-idx, 0xC240 variant, 0xC25B stage, score, lives), zero scroll 0xC214, JP 0x00A3. Respawn resumes mid-stage at saved wave-index, NOT a stage restart.
- **GAME OVER screen** `0x02DC / handler 0x0FC0` [ROM-EXACT/high]
  0x02DC (final, both players out): LD A,13;LD (0xC980),A (spawn text entity type 0x0D), sound 0xDC00=0x86, delay BC=0x168(360 frames) of RST8, then JP 0x1D40 (title). 2-player variants 0x0286/0x02B1 branch on 0xC102 bit2/bit3 to hand off to the other player or reset. Entity type 0x0D handler @0x0FC0: sets IX+9=0x40(Y=64),IX+11=0x60(X=96),IX+3=0x1E (or 0x1F if 0xC243 bit0 clear) = 'GAME OVER' metasprite frame group; drawn via 0x21E3/0x2276.
- **Zone-clear / intermission (banner + scroll wipe + fanfare)** `0x0E60-0x0EF2 / banner 0x0FF9` [ROM-EXACT/high]
  Boss-clear path ~0x0E60+: 0x0E92 LD HL,0xC8;LD (0xC291),HL (200-frame transition delay); 0x0E98 spawn banner entity type 0x0B @0xC980 and type 0x0C @0xC940; realign scroll (0xC216&=0xF8); recompute wave-index 0xC211; zero scroll 0xC214/0xC215; clear boss flags 0xC2C1=0,0xC2C0=1; set fast transition scroll 0xC223=0xF000; 0x0EDA loop B=14 {CALL 0x0CFC;CALL 0x0EF3} = 14-step scroll wipe (bank6); restore 0xC223=0xFF80. Banner handler type 0x0B @0x0FF9: Y=0x30,X=0x60, IX+3=0x20+0xC25B (per-stage title tiles), IX+0x10=0xB4 lifetime -> lives 180 frames then self-kills. Fanfare cue 0xDC00=0x91 emitted in scroll routine at 0x0D14.
- **Zone / loop progression mechanics** `0x0D03-0x0D43 / BGM 0x00D3` [ROM-EXACT/high]
  Scroll routine 0x0D03: LD A,(0xC290);OR A;JR z (normal scroll). When 0xC290=1 (transition pending, set at 0x2369), countdown 0xC291 (0x0D09), on expiry: sound 0xDC00=0x91, clear 0xC290, set 0xC23A=1 (screen-redraw). 0x0D21 variant advance: LD A,(0xC240);ADD 1;DAA;LD (0xC240),A. 0x0D2A loop counter: LD A,(0xC227);INC;LD (0xC227),A (monotonic completed-stage count). 0x0D31 stage = 0xC227 mod 3: SUB 3/JR nc/ADD 3;LD (0xC25B),A (0=Galaxy,1=Asteroid,2=Nebula). Reset scroll 0xC214=0,0xC216=0. Per-zone BGM: 0x00D3 LD A,(0xC25B); index table @0x00E2 = {0x82,0x83,0x92}; LD (0xDC00),A.
- **LOOP DIFFICULTY RAMP: variant select = 0xC240 mod 3** `0x3F62-0x3F6B` [ROM-EXACT/high]
  Wave spawner 0x3F62: LD A,(0xC240); 0x3F65 SUB 3;JR nc,0x3F65;ADD 3 = 0xC240 mod 3; indexes root table 0x3FA3 (3 variant pointers 0x3FA9/0x4029/0x40A9 = Galaxy/Asteroid/Nebula). Since 0xC240 increments once per zone and stage=0xC227 mod3 tracks it, every loop replays the same three rosters (no roster change per loop, no spawn-rate scaling in the spawn layer).
- **LOOP DIFFICULTY RAMP: enemy fire gated behind 0xC240 >= 3** `0x5C06 / caller 0x5BF2` [ROM-EXACT/high]
  Fire predicate 0x5C06: LD A,(0xC240);CP 3;RET (carry set iff 0xC240<3). Caller 0x5BF2: CALL 0x5C06;JR nc,0x5BF9; if carry (0xC240<3) fall to 0x5BF7 XOR A;RET = suppress fire. Because 0xC240 only BCD-increments per zone (0x0D21) and is never reset (only restored on respawn), it is 0/1/2 across the three zones of loop 1 -> enemy fire is SILENT the entire first loop, and ARMS at 0xC240>=3 (start of loop 2) and stays armed thereafter. (Prior work: type 0x19 fires ungated on loop 1.) Enemy-fire SFX cue 0xDC00=0x8C (0x5C14).
- **CORRECTION: sub_2309 / 0xC238 is a palette-cycle ANIMATION, not progression** `0x2309-0x23A0` [ROM-EXACT/high]
  0x2309: RET if 0xC100==0; DEC (0xC239); RET nz; reload 0xC239=15 (runs every 15 frames). 0xC255==0 branch (0x231D): 0xC238=(0xC238+1) mod 6 (INC;CP 6;JR c;XOR A), then RST 0x20 copies sliding windows from tables 0x23A1/0x23A8/0x23AF into CRAM entries 0x0B-0x0C / 0x0D / 0x0E (triangle-wave values 03,02,01,00,01,02,03 etc = background color pulse). So 0xC238 wrapping at 6 is a 6-phase palette pulse, NOT the zone/loop counter. The 0xC255!=0 branch (0x234F) is the boss-approach palette FADE: steps 0xC257 0..6 writing full 16-entry BG palettes from per-stage table 0x23B6 -> {0x23BC,0x242C,0x249C}; at 0xC257==6 it spawns scripted end-boss anchor type 0x2A @0xC9C0 and sets transition 0xC290=1. This overturns the prior-doc inference that sub_2309 drives zone progression.
- **CORRECTION: NO ending/credits screen exists -- game loops forever** `0xC227 (no CP) / 0x3B94-0x3BA8` [ROM-EXACT/high]
  Loop counter 0xC227 is only read to save-to-checkpoint (0x0177/0x01B7/0x0200), restored (0x0253), and incremented (0x0D2A) -- it is NEVER compared to any limit. Scripted end-boss driver 0x3B94 dispatches purely by 0xC25B via table 0x3BA8 -> {0x3BAE,0x3C6C,0x3CFF} (Zanoni/Nebiros/Belzebul) with no loop-count branch; on boss-defeat (0xC2C1) it just sets 0xC255=1 to start the fade->zone-advance. Whole-ROM ASCII scan finds no GAME OVER/CONGRATULATIONS/THE END/CREDITS/STAGE strings and no credits routine. Beating Belzebul (any loop) -> fade -> stage=0xC227 mod3=0 (Galaxy) again. The task/prior-doc claim of an ending 'after the 3rd Belzebul' is not supported by the code.
- **High-score: single value, continuous update; NO name/initials entry** `0xC030-C032 / update 0x2126` [ROM-EXACT/high]
  Hi-score buffer 0xC030-0xC032 (3 BCD bytes). Update 0x2126: SBC-compare live score 0xC234..0xC232 vs hi 0xC032..0xC030 (B=3, from low byte); RET c if live<hi; else 0x2136 LDIR live 0xC232-C234 -> 0xC030-C032. Runs every scoring event, so the hi-score tracks the live score during a first playthrough. Title displays it via the name-table 'HIGH SCORE'/'n PTS.' text plus the HUD digit drawer (0x217E/0x21B5 reading score 0xC232). Whole-ROM scan finds NO 'NAME'/'ENTER'/'RANKING' text and no A-Z cycling-input routine -> there is no initials/name-entry screen; the high score is a single anonymous number.
- **Sound/music cue latch 0xDC00 and its flow cues** `0xDC00 (cues @0x1DE9/0x00E2/0x028F/0x0D14)` [ROM-EXACT/medium]
  RAM byte 0xDC00 is the sound-driver command latch (written across flow states, consumed by the audio driver each frame). Observed flow cues: 0x81 = title/attract start (0x1DE9); 0x82/0x83/0x92 = per-zone BGM by 0xC25B via table 0x00E2 (0x00D3); 0x86 = game over (0x028F/0x02E4/0x02BE); 0x8A = event/pickup jingle when 0xC298 set (0x037C); 0x91 = zone-clear fanfare (0x0D14); 0x8C = enemy-fire SFX (0x5C14). (Values are ROM-exact; the musical identity of each track ID is inferred by the state that triggers it.)
- **Extra-life award thresholds (score-based)** `0x20FF-0x211D / table 0x211E` [ROM-EXACT/medium]
  Score-add path 0x20FF: LD A,(0xC263);CP 4;RET nc (max 4 awards); compares score against table @0x211E = 00 05 / 00 10 / 00 15 / 00 20 (16-bit LE 0x0500,0x1000,0x1500,0x2000) via 0x1EB5; on cross, 0x2110 LD A,(0xC23F);ADD 1;DAA;LD (0xC23F),A (grant one BCD life) and INC (0xC263). Interpreting the BCD score scale this is ~every 50,000 up to 4 lives; consistent with prior 50k note but the exact multiplier depends on the score digit alignment.

### Swift port impact
GameSim's Mode machine (currently title/playing/boss/gameOver with a dead-end restart) must be rebuilt around a 0xC100-equivalent flag with these exact edges: title <-> attractDemo alternation driven by frame timers (title=1080 frames on 0xC020, demo=1800 at 0x1E20); demo plays back a recorded input tape (ship the two ROM tapes or record equivalents) and any fire returns to title; RESET (VBlank, port 0xDD bit4) always jumps to title; PAUSE (NMI, flag 0xC111) only toggles in-game and freezes the subsystem tick. Gameplay is one continuous superloop across all zones+loops -- do NOT model per-zone as separate 'playing' states; only death breaks out. Death = BCD lives-- (start 3, 0xC23F) then RESPAWN AT THE SAVED WAVE-INDEX CHECKPOINT (0xC211..+8, variant 0xC240, stage 0xC25B, score) -- not a stage restart; lives==0 -> 360-frame GAME OVER banner -> title. Zone-clear = 200-frame banner (per-stage frame group 0x20+stage, 180-frame lifetime) + 14-step scroll wipe + fanfare, then stage = completedCount(0xC227) mod 3 and variant 0xC240 BCD++. ### Summary
Fully decoded the power-up/weapon subsystem, closing the two gaps the prior docs left open (the block counter and the ladder-effect mapping). The block counter is 0xC228: the block-object break handler at 0x2883 does INC A / CP 12 / on >=12 sets pickup-request 0xC615=1 and resets the counter to 0 — so a pickup spawns EVERY 12 blocks, not at cumulative 12/36/60/84/108/120. Which pickup you get is driven by a separate ladder index 0xC229 that indexes a 10-entry kind-sequence table at 0x0C98 (or 0x0CA8 when drones were cheat-granted). The kind codes are 0x0F=laser, 0x10=drone, 0x11=triple, 0x12=speed. Decoding the sequence shows speed-ups land at block counts 12,36,60,84,108,120 — EXACTLY the manual's list — with weapon/drone tiers interleaved at 24(triple)/48(laser)/72(drone1)/96(drone2). The weapon form is NOT 0xC264 (that is a random cosmetic ship-graphic page selector); it lives in the player-entity fields 0xC610(+0x10)=laser flag, 0xC616(+0x16)=triple flag, 0xC613(+0x13)=speed index (init 3). The player/weapon handler is 0x0807; its fire block (0x093E-0x09D9) picks a bullet-form code from (laser,triple) and spawns one bullet from the player plus one from each active drone. Single vs triple is a hitbox WIDTH difference (8px vs 16px), not a 3-way angular spread or extra projectiles; laser is a persistent, piercing beam that grows over 3 frames. Laser (0xC610) is the flag that one-shots the 8-HP triat (verified in the triat handler at 0x5466). Drones are entity slots 1 & 2 (0xC640 type 8, 0xC680 type 9) that trail the ship along a recorded position ring at 0xD000/0xD100.

### Findings
- **Power-up BLOCK COUNTER = 0xC228 (threshold 12, wraps to 0)** `0x2883-0x2894` [ROM-EXACT/high]
  Block-break object handler at 0x2883: LD A,(0xC228); INC A; CP 12 (FE 0C); JR c,0x2891 (store back if <12); else LD A,1 / LD (0xC615),A (request pickup) / XOR A; then LD (0xC228),A. So 0xC228 counts destroyed background blocks and wraps every 12, firing pickup-request flag 0xC615=1. This is the counter the prior docs said was NOT yet found.
- **Pickup KIND ladder: index 0xC229 -> table 0x0C98/0x0CA8** `0x0879-0x089A` [ROM-EXACT/high]
  Player handler at 0x0879: LD A,(0xC229); CP 0x0A; if >=10 -> fill-logic at 0x089C; else INC and use as index. Table base 0x0C98 (or 0x0CA8 if 0xC250 set) + index -> kind byte written into pickup slot type. 0xC229 is incremented BEFORE use (first pickup uses index 1) and caps at 10. Index advances per pickup SPAWNED, independent of collection.
- **Ladder sequence tables (kind codes)** `0x0C98 / 0x0CA8` [ROM-EXACT/high]
  0x0C98 (normal) = 12 12 11 12 0F 12 10 12 10 12 12...; 0x0CA8 (drones-via-cheat) = 12 12 11 12 0F 12 12 12 12 12. Kind codes: 0x12=SPEED, 0x11=TRIPLE, 0x0F=LASER, 0x10=DRONE. Effective sequence (idx1..10): speed,triple,speed,laser,speed,drone,speed,drone,speed,speed. idx>=11: grant triple-if-missing, else laser-if-missing, else nothing (0x089C-0x08B4).
- **Threshold->effect ladder reconciles the manual 12/36/60/84/108/120** `0x2883 + 0x0879 + 0x0C98` [MEASURED/high]
  Pickups appear every 12 blocks (12,24,36,48,60,72,84,96,108,120). Mapping to kinds: 12=SPEED,24=TRIPLE,36=SPEED,48=LASER,60=SPEED,72=DRONE1,84=SPEED,96=DRONE2,108=SPEED,120=SPEED. The speed-ups fall at 12/36/60/84/108/120 == the manual's list; weapon/drone tiers are the interleaved 24/48/72/96. The manual list = the speed rungs, not the pickup interval.
- **Weapon-form flags live in the PLAYER entity, not 0xC264** `0x08CB-0x0908` [ROM-EXACT/high]
  0xC610 (player +0x10) = LASER flag; 0xC616 (player +0x16) = TRIPLE counter/flag; 0xC613 (player +0x13) = SPEED index (init 3 at 0x081D). Pickup application in player handler: 0xC61F==0x11 -> INC (IX+0x16)/triple (0x08D2); ==0x12 -> INC (IX+0x13)/speed (0x08DB); ==0x0F -> LD (0xC610),1/laser (0x08E4); ==0x10 -> grant drone (0x08EB); else -> death (0x090A).
- **Pickup collection via shared AABB collision (bit6 + type into +0x1F)** `0x1ACB-0x1B13` [ROM-EXACT/high]
  Collision resolver at 0x1ACB-0x1AEC: on overlap SET 6,(IY+1); (IY+0x1F)=IX type; SET 6,(IX+1); (IX+0x1F)=IY type. So the player records the pickup's type in 0xC61F and bit6. Player handler 0x08C0 gates on BIT 6,(IX+1). Non-pickup types fall through to death. Hitbox AABB built from table 0x1B1C+(IX+3)*4 at 0x1AEF.
- **Fire routine: form selection + cadence** `0x093E-0x09D9` [ROM-EXACT/high]
  0x093E-0x09D9: 0xC014&0x30 gates any fire; 0xC012&0x30 (fresh-press edge) fires immediately and reloads (IX+0x11)=0x20; else 0xC013&0x30 (held) DEC (IX+0x11), fire+reload 0x20 (=32 frames) when it hits 0. Form code H from (laser,triple): (0,0)->0x0B single, (0,>=1)->0x0C triple, (>=1,0)->0x0D laser, (>=1,>=1)->0x10 wide-laser. Spawns 1 bullet (player) + 1 per active drone into pool 0xC6C0. - **Weapon geometry (single vs triple vs laser) from hitbox table 0x1B1C** `0x1B1C-0x1B64` [ROM-EXACT/high]
  Table 0x1B1C, 4 bytes [Yoff,H,Xoff,W], index=bullet +3=H. 0x0B single: E8 20 FC 08 = 8w x 32h. 0x0C triple: E8 20 F8 10 = 16w x 32h (DOUBLE-WIDTH single projectile, not 3 angled shots).   Fire routine iterates IY=0xC6C0, stride 0x40, up to 6 slots (entity slots 3-8) to place bullets; player init at 0x0841 also sweeps 0xC6C0 x6 setting active bits. The drones themselves are slots 1&2 (0xC640/0xC680). The task's '6-slot drone sub-pool @0xC6C0' is actually the bullet pool.
- **CORRECTION: 0xC264 is a random cosmetic ship-graphic selector, not the weapon tier** `0x0821-0x0832, 0x1E26-0x1E2B, 0x092A-0x093B` [ROM-EXACT/high]
  0xC264 set by LD A,R; AND 1 at 0x1E26 (pseudo-random 0/1 at stage init). Read at 0x0821: if 0 -> HL=0xAA00 else 0xB100, stored to tile-source pointer 0xC260 (0xC262=1). ### Verifier additions (load-bearing facts the decode missed or under-stated)
- Alt-death trigger +0x1E==3 (open question they could not source): a SET exists at 0x25A2 — LD (IX+0x1E),A — inside a background/tilemap-collision routine that reads a tile-property byte via pointer 0xC236 (or 0xC25E when 0xC256 set) + column index (0x2590-0x25A2).
